Upgrading from 0.4.2 needs steps on the host. Before you pull the image: upgrade the Wyrwood controller and agents to 0.7.1 first, in Wyrwood's upgrade order; back up the `/var/lib/menagerie` volume, as going back needs it; repair a workspace definition that no longer parses; make each `templates` entry name a `MAJOR.MINOR.PATCH` tag (an entry on a host with a port takes no ref: register that template in the interface after the first start instead); and point clients at the template ids that are kept, as the import keeps only the newest entry's id for each repository and folder and a create naming another entry's id is refused as `unknown-template`. With `provisioning.xolotl`, set `provisioning.xolotl.key-policy` before the first start, and this covers existing workspaces: every workspace whose definition has a `customizations.menagerie` block and no Xolotl key gets a new client key `<key-policy>/<name>` at its next Start or Rebuild, where 0.4.2 issued one only when the template declared `xolotl` (keys a 0.4.2 template declared are imported at the first start). Without `key-policy`, that Start or Rebuild fails as `provisioning-unavailable`. A workspace whose name is not 1 to 63 lowercase letters, digits, `_` or `-`, starting with a letter or digit, fails every Start and Rebuild as `provisioning-invalid`, so before the upgrade list such workspaces, recreate each under a valid name, move its work and delete the old one; a delete still works after the upgrade. After the first start: read the start log for the entries it skipped and register those templates in the interface, then remove the `templates` key; with `provisioning.wyrwood`, mark as required, or put in groups, the policies your templates used to declare, before anyone creates a workspace; and stop sending `templateId` on an upgrade, which is refused as `invalid-request` (an upgrade without it applies the current version of the workspace's template). A new workspace name on a host with provisioning follows the same name rule.
