# Changelog

## 0.5.1

### Features

- Workspaces can back up to different Git repositories. A new **Backups** screen registers a backup repository with a display name and a Git URL once Menagerie has proved it can write to it, and removes one no workspace backs up to. **New workspace** asks which backup repository the workspace backs up to, choosing the only registered one for you, and the workspace list shows where each workspace backs up to. The create job request takes an optional `backupRepositoryId`. The first start of this release registers the configured `workspace-repository` once and keeps every existing workspace backing up to it; the key is then optional and no longer read, and each start that finds it logs a warning, so remove it after that start.
- A workspace's backups can move to another registered backup repository: **Move backups** on its row starts a `move-backup` job that checks Menagerie can write to the destination, refuses a destination whose branch of the workspace's name holds another history (`backup-branch-conflict`), commits and pushes a current backup there and reads it back, and only then makes the destination the workspace's repository. A failed move (`backup-move-failed`) keeps the earlier repository and says why, and the earlier repository keeps its branch for recovery. A workspace with no backup repository gets its first the same way. New `job-limits.operations.move-backup`.

## 0.5.0

### Breaking

- Register templates in the interface, with no configuration change or restart. A manager registers a template from its Git address, and Menagerie refuses one that fails a check, naming it: its address, listing its versions, a release tag, fetching and reading it, and `.devcontainer/devcontainer.json` in its files. A version is a release tag `MAJOR.MINOR.PATCH` of the template's repository; a manager upgrades a template to a newer version, and an upgrade of a workspace applies its template's current version and no longer takes a `templateId`. Templates can be renamed, given a runner image, and removed while no workspace uses them. The first start imports the configuration's `templates` entries once, one template per repository at its newest version, and names by id the entries it skips; the key is no longer read, and each start warns while it is present. The template service refuses folder, `file://`, `git://`, `http://` and template-name addresses, and any address with a password. An upgrade that names `templateId` is refused as `invalid-request`; an upgrade without it applies the current version of the workspace's template, so upgrade the template first to take a newer version. The import keeps one template per repository and folder, with the newest entry's id: a create naming another entry's id is refused as `unknown-template`, so point clients at the id that is kept before you upgrade. It skips a repository none of whose entries names a `MAJOR.MINOR.PATCH` tag (a leading `v` is accepted), an entry on a host with a port that names a ref, and an address the template service refuses; the start log names each skipped entry, so register those templates in the interface, then remove the `templates` key.
- Upgrading from 0.4.2 needs steps on the host. Before you pull the image: upgrade the Wyrwood controller and agents to 0.7.1 first, in Wyrwood's upgrade order; back up the `/var/lib/menagerie` volume, as going back needs it; repair a workspace definition that no longer parses; make each `templates` entry name a `MAJOR.MINOR.PATCH` tag (an entry on a host with a port takes no ref: register that template in the interface after the first start instead); and point clients at the template ids that are kept, as the import keeps only the newest entry's id for each repository and folder and a create naming another entry's id is refused as `unknown-template`. With `provisioning.xolotl`, set `provisioning.xolotl.key-policy` before the first start, and this covers existing workspaces: every workspace whose definition has a `customizations.menagerie` block and no Xolotl key gets a new client key `<key-policy>/<name>` at its next Start or Rebuild, where 0.4.2 issued one only when the template declared `xolotl` (keys a 0.4.2 template declared are imported at the first start). Without `key-policy`, that Start or Rebuild fails as `provisioning-unavailable`. With `provisioning.xolotl`, a workspace that has a `customizations.menagerie` block and no Xolotl key, and whose name is not 1 to 63 lowercase letters, digits, `_` or `-`, starting with a letter or digit, fails every Start and Rebuild as `provisioning-invalid` once `key-policy` is set. A workspace whose 0.4.2 definition declares `customizations.menagerie.xolotl` keeps the key imported at the first start, a workspace with no block is not provisioned, and a host without `provisioning.xolotl` issues no key: none of those is affected. Before the upgrade, list the affected workspaces, recreate each under a valid name, move its work and delete the old one; a delete still works after the upgrade. After the first start: read the start log for the entries it skipped and register those templates in the interface, then remove the `templates` key; with `provisioning.wyrwood`, mark as required, or put in groups, the policies your templates used to declare, before anyone creates a workspace; and stop sending `templateId` on an upgrade, which is refused as `invalid-request` (an upgrade without it applies the current version of the workspace's template). A new workspace name on a host with provisioning follows the same name rule.
- Choose workspace policies at creation and edit them on the workspace row. Apply stored selections immediately through Wyrwood 0.7.1 without a rebuild, retain imported identities, and show pending or failed application. Policies a template declares (`customizations.menagerie.wyrwood.policies`, `customizations.menagerie.wyrwood.values` and `customizations.menagerie.xolotl`) are no longer read: mark the policies every workspace needs as required, or put them in groups, on the Policies screen before anyone creates a workspace. With `provisioning.xolotl`, a workspace whose definition has a `customizations.menagerie` block and no Xolotl key gets a new client key `<key-policy>/<name>` at its next create, start or rebuild, and that fails as `provisioning-unavailable` until `provisioning.xolotl.key-policy` is set, as the key policy no longer comes from a template. 0.4.2 issued a key only when the template declared `xolotl`; keys a 0.4.2 template declared are imported at the first start. Menagerie needs Wyrwood 0.7.1 or later, up from 0.6.1: upgrade the Wyrwood controller and agents first. The configuration guide covers the host's key policy and policy recovery.

### Features

- Menagerie keeps what it provisioned in its own data, a SQLite database in the data volume, in place of the definition and the retirement records: a delete removes each Wyrwood binding and Xolotl key Menagerie made for a workspace, also when its definition no longer parses or declares them, and any job that ends with the devcontainer started retires what the definition no longer declares. A binding that Wyrwood answers is outside the operator key's grant stays recorded and fails the job as the new error `binding-outside-grant`. A workspace whose folder is gone and that still holds a binding or a key is listed as `no-folder` and can be deleted, and a create is refused `workspace-exists` while Menagerie holds a workspace of that name. The first start takes over each workspace, its retirement records and what its definition declares, with no step by hand. Back up the `/var/lib/menagerie` volume with the host.
- Manage required Wyrwood policies and single-select or multi-select policy groups, with grant checks and revisioned workspace selections.
- Menagerie finds new versions of each registered template by itself, when it starts and every `template-versions.every` (an hour by default), and on request with **Check versions**, with no restart. The Templates screen shows each template's newest found version and its last check, and a failed check keeps the versions found before. A template is upgraded to a version a check found, chosen from a list, and a moved tag refuses creates and upgrades until the template is upgraded to that version again. Each workspace shows the version last applied to it, an unknown one, and whether it needs an upgrade. An upgrade compares that stored version, and one whose version is unknown goes on only when the current version descends from its applied commit. Apply branch refuses a branch whose applied record would move the workspace backward. The first start of this release records each workspace's applied version from its applied record.

### Fixes

- A template address on a host with a port takes no ref: in an `https://` or `ssh://` address no `:` may come before an `@`, so a password that holds a `/` is refused before any fetch. Register such a template without its ref, which takes the newest version; the first start skips a `templates` entry of that shape and names it by id.
- A job names the Wyrwood operator key it cannot use: a key that `ssh-agent.sock` does not offer is named by its selector in `provisioning.wyrwood.operator-key`, a public key by its fingerprint, and a key Wyrwood has not approved (pending, rejected or revoked) by its fingerprint. Wyrwood shows a key it is newly offered as pending.
- The new `operations.apply-policies` job time limit bounds a policy application, as the other operations' limits bound theirs.
- A throwaway container, which runs a template hook, `initializeCommand` or a bind source check, has a two-minute bound on its create, apart from the 30-second bound on removing it. A create that passes it fails with "the Docker daemon did not answer in time while creating the throwaway container; retrying is safe".
- A template request whose job is cancelled or times out stops its fetch and writes no further file, and a stalled schema endpoint no longer holds a job. The template service runs on Toha 0.5.0.
- Known issues, not fixed in this release and left open: the workspace list and upgrade screens differ from the approved mockup in the controls, the order of the actions and the upgrade heading ([#127](https://github.com/wyrd-company/menagerie/issues/127)); and an upgrade or Apply branch job that runs while a version check fills in an unknown applied version can record a lower version number than the check found, with no content going back ([#128](https://github.com/wyrd-company/menagerie/issues/128)).

## 0.4.2

### Fixes

- An interview of more than one batch of questions moves on from a batch accepted as shown: a re-answered upgrade no longer asks that batch again. The web UI now sends every question it shows, the untouched ones with their defaults, and the template service answers a question a submission leaves out with its default.

## 0.4.1

### Features

- An upgrade can ask every question again: **Ask every question again** on the upgrade screen, or `reanswer` on an `upgrade` job, asks every question with the workspace's recorded answers as the defaults, so an answer can take an option the new template version adds.

## 0.4.0

### Breaking

- A workspace whose rendered definition has a `customizations.menagerie` block is provisioned by its jobs, with no step in a CLI or a web interface: Menagerie issues its Xolotl client key, makes its Wyrwood binding, creates its container, waits for its sockets and only then starts it. A create, start, rebuild, upgrade and apply-branch run the steps, each its own phase in the job console, and **Start** retries a job that failed without rotating the key or writing the binding again. A new create no longer overwrites a deleted workspace's backup branch: it copies the branch to `archive/<name>-<UTC stamp>` first. New configuration `provisioning.readiness-wait`, new phases `issue-key`, `bind`, `wait-for-sockets`, `verify` and `retire`, and new job errors `provisioning-invalid`, `provisioning-unavailable` and `provisioning-not-ready`.

### Features

- Run templates that declare empty directories and user sections, through Toha 0.4.1. Honor a container name from `runArgs` and read-only mount object targets, through devcontainer-builder 0.2.1.
- Add `provisioning.wyrwood`, which locates the Wyrwood controller and selects the operator key that will manage workspaces' bindings. Menagerie offers the controller only that key, pins its host key, and names the key's fingerprint when it has no approval. Provisioning needs Wyrwood 0.6.1 or later.
- Add a delete operation. **Delete** on a workspace's row asks for its name, stops the devcontainer, commits and backs up, removes its Wyrwood binding, containers and Xolotl key, then removes its socket folder and folder. A failed delete can be retried. Ignored files are not backed up and are lost.
- Create the missing bind source folders inside a workspace before each start and rebuild. Check a new workspace's bind sources outside its folder and its network before its first commit, and report all that are missing at once as `host-prerequisites-missing`.
- Mint a T3 Code pairing token for a running workspace from its row in the workspace list, or with `POST /api/workspaces/{name}/t3-code-pairing-tokens`. The token is minted in the workspace's container through Docker exec, and Menagerie keeps no copy.
- Run workspaces through devcontainer-builder 0.3.0, which honors more of a definition's `runArgs`, `mounts` and build options. A `mounts` string now follows Docker's `--mount`: without `type=` it is a volume, and a space around a field or a value is refused. A lifecycle command of an unsupported type now fails when the definition is read. A new `create-container` phase can take a time limit.
- Accept `provisioning.xolotl`, the Xolotl URL and the OpenBao secret of the scoped key that issues and revokes workspace client keys. Requires Xolotl 0.6.0 or later.

### Fixes

- A generate or upgrade whose job was cancelled or reached its time limit while a template fetch ran no longer writes to the workspace folder when that fetch returns.
- The deployment example mounts the Wyrwood consumer directory in long form with `create_host_path: false`, so Docker never creates a missing directory as root and Menagerie returns after a host restart with no step by hand. A first install creates the directory once before `docker compose create`.
- The template service removes what a killed upgrade left in its candidate folder when it starts: Toha's temporary entries and the workspace service's copy-back folders, each named in its log. It leaves every other entry.
- A folder in the workspace root whose name starts with a dot, such as `.shared`, is not a workspace: it is not listed, and an operation that names it is refused as `invalid-workspace-name`.

## 0.3.0

### Features

- Jobs can have configured time limits, per operation and per phase, that cancel a job as timed-out without counting time spent waiting for answers, and a webhook can be told about failed and long-running jobs.
- A devcontainer definition reads only the variables of Menagerie's environment that the new `local-env` setting lists, through `${localEnv:NAME}`, Compose interpolation and `initializeCommand`. Without `local-env` it reads none: a definition that used another variable now gets its default value, and the job log names the variable. Add the variables a definition needs to `local-env`.
- Template hooks and initializeCommand run in throwaway containers that mount only the workspace folder, so they cannot reach the Docker socket, the Wyrwood sockets or Menagerie's environment. Hooks run in a template's runner-image, initializeCommand in the global runner-image, and both default to Menagerie's own image; hook output the template does not capture now appears in the job console. A job cancelled at a time limit removes its running hook containers before it ends.
- Authenticate to GitHub with a GitHub App: backups push and private https templates fetch with short-lived installation tokens, minted through the App key held in OpenBao Transit, with no machine user and no SSH key. SSH stays for other hosts.
- The template service signs the interview session it hands to the browser. It refuses a session that was altered, is unsigned, or was issued for another workspace, template or flow, with the error `session-tampered`. The signing key is kept as `toha/session-key` in the `/var/lib/menagerie` volume, so interviews continue across a restart of the template service.
- Menagerie commits and backs up workspace changes as a new `commit` job: it records every change as `git add --all` would, leaving ignored files and nested repositories out, and pushes the workspace branch. With `auto-commit: {every: 1h}` it commits every idle workspace that has changes on a schedule. With `workspace-socket: {folder: ...}` each devcontainer gets a socket at `/run/menagerie/workspace.sock` and the client `/run/menagerie/bin/workspace-commit`, which commits and backs up its own workspace; a second commit within `min-interval` (1m by default) is refused. Existing devcontainers get the socket at their next rebuild.
- Apply branch brings a branch of the workspace repository, such as a reviewed pull request's head, into a workspace from its row in the workspace list or as the `apply-branch` job. Menagerie fetches only that branch, commits and backs up local changes, then fast-forwards the workspace or merges it file by file, backs up and rebuilds the devcontainer. A branch that would not apply cleanly (a file both sides changed, an untracked or ignored file in the way, a submodule) fails as `not-applicable` and lists the paths, with nothing applied. Propose changes to a workspace as a pull request whose base is its branch, do not merge it on the forge, and apply its head branch.

## 0.2.0

### Features

- The web UI has a new look: a plain operations console with the Menagerie logo, and a dark theme that follows the operating system setting.

## 0.1.0

### Features

- Menagerie's first release: a web UI where managers sign in through OpenID Connect, create workspaces from approved Toha templates, start, stop and rebuild their devcontainers, and upgrade them to newer template versions, with each workspace backed up to its own Git branch. It ships as one container image for Linux amd64 and arm64.
